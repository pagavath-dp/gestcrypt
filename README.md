# GestCrypt

GestCrypt is a local, gesture-assisted cryptographic vault and gesture-reliability research prototype. The user-facing Vault creates and opens **V3 files only**. Normal access requires a fresh match to a separately enrolled Vault gesture, a passphrase, and this browser profile's non-extractable local key. Emergency recovery uses the file-specific recovery key instead. Gesture matching is an application-level gate, not cryptographic key material or proof of identity or liveness. Historical V1/V2 modules remain for regression tests and the synthetic Security Attack Lab; the Vault does not open those formats or fall back to them.

## Run and test

From this directory, run `python3 -m http.server 8000`, then open `http://localhost:8000` or `http://127.0.0.1:8000` in a current Chrome browser. **Choose one address and keep using it:** they are different origins with separate IndexedDB device keys and Vault gesture enrollments. Switching addresses does not carry normal-access credentials across. The browser needs Web Crypto and IndexedDB; normal Vault access and Gesture Calibration also need camera permission and a secure context such as localhost or 127.0.0.1. Emergency recovery needs neither camera permission nor the original profile. Internet access is currently required for Tailwind; camera features additionally load MediaPipe JavaScript/WASM and the hand-landmarker model. No backend is used by this repository; the application code does not upload selected files or keys, but externally loaded code is part of the trust boundary.

Run local automated tests with `node --test tests/*.test.mjs` using Node.js 24 or later. Run the offline analysis tests with `python3 -m unittest discover -s tests -p 'test_*.py'`. The automated suites use deterministic or simulated inputs; they do not require a camera or network and do not establish real-camera reliability or cross-browser security. Core Vault and study workflows were also exercised manually in Chrome during development, separately from automated testing. Those acceptance checks do not cover every browser, device, environment, or failure scenario; repeat the relevant checks for the release environment.

The single-page interface has four sections: **Vault** for encryption, decryption, emergency recovery, and rebind; **Gesture Calibration** for camera capture and study recording; **Security Attack Lab** for synthetic demonstrations; and **Evaluation Results** for the validated exploratory pilot `STUDY-1873C987`. The results section links to the existing pilot report, aggregate metrics, and six figures in `analysis-output/`; it does not show unvalidated or live held-out results. The camera panel is shared by normal Vault access and calibration. Switching sections does not stop an already active camera.

### Vault workflow

Select **Set up local device key** once in the intended browser profile, then select **Start gesture enrollment** and initiate two separate matching capture steps. The Vault template is held in a dedicated, versioned IndexedDB store, separate from study records and localStorage. New encryption requires an enrolled template, a fresh gesture capture, a nonblank passphrase of at least 12 characters, and the profile key. Each file gets a fresh random 256-bit data key and an independent random 256-bit recovery key. After encryption, explicitly copy or download the recovery key, confirm **I saved this file's recovery key**, then download the encrypted file. The key is displayed only while that download is pending; the app does not persist it. Losing the recovery key and normal access makes the file unrecoverable. A copy action places the key on the operating system clipboard; clear it when finished.

Normal decryption starts a new gesture capture for every file and also requires the correct passphrase and original browser profile. The Vault rejects unsupported files before capture or key derivation. **Recover plaintext** is a separate action using only that file's recovery key; it requires no camera, passphrase, or original profile. **Rebind** authenticates the old file through its recovery key, then creates a new encrypted file protected by the current profile, a new passphrase, and a fresh independent recovery key. It preserves the original file and ciphertext; the original key continues to recover the original file but does not recover the rebound file. Back up and acknowledge the new key before downloading the rebound file. Rebind does not silently create a local device key; set up the new profile explicitly first. A malformed file or failed authentication produces no plaintext download.

Whole-file encryption is limited to 32 MiB of plaintext. The Vault buffers whole files in browser memory; this is a supported limit, not a cross-browser performance measurement. Browser storage loss makes normal access unavailable, so keep each file's recovery key separately. The non-extractable device key and nonce counter are stored in a separate IndexedDB database; the counter is committed before each nonce is returned. Web Crypto non-extractability is not hardware-backed authentication or a guarantee against malicious same-origin code. Restoring an old browser-profile database backup could roll the counter back and is outside the application's guarantees. Same-origin malicious JavaScript can bypass the gesture gate and invoke cryptographic functions, so the Vault does not claim two independent cryptographic factors or replay resistance. Losing both normal access and the independent recovery key makes a file unrecoverable; theft of a file and its recovery key permits emergency recovery. Browser acceptance remains specific to the environments and scenarios actually checked.

## Gesture processing

MediaPipe supplies 21 world landmarks per detected hand. GestCrypt computes five finger-extension ratios and three spread angles, gathers 25 accepted frames, and summarizes each feature by its median and standard deviation. Finger ratios use thresholds 1.30 and 1.70 (thumb: 1.15 and 1.60); spread uses 12 degrees. Values below the first ratio threshold map to 0, values from the first up to but excluding the second map to 1, and values at or above the second map to 2. Spread at exactly 12 degrees maps to 0. Spread contributes only when both adjacent fingers are fully extended. The signature begins with `GC1:`.

### Capture ambiguity policy

The hand detector is configured for up to two hands. Five consecutive processed frames with exactly one valid image-landmark set and one valid world-landmark set establish readiness. In Test mode, pressing a capture button records the attempt, then waits for a newly processed valid readiness observation before starting its fresh 25-frame capture; this prevents a blocking reference-confirmation dialog from using old readiness. If readiness does not return within 10 seconds, that same attempt is recorded as `not_ready`. Every accepted capture frame must contain exactly one valid hand. A detected second hand, no hand, inconsistent landmarks, camera/model error, stale frames, or a 10-second capture timeout cancels the attempt and clears its buffer. The user must press a capture button again after readiness returns; frames from a failed attempt are never reused. Capture messages appear beside the camera in a live status region.

Frame sampling uses `requestVideoFrameCallback()` and its presented-frame counter when available. The fallback polls `getVideoPlaybackQuality().totalVideoFrames`; it does not use the continuously advancing playback clock as a frame identifier. If neither counter is available, camera capture is unavailable. Both paths avoid counting the same presented frame twice, but processing can skip frames when inference is slow. An event that appears and disappears entirely between processed frames may therefore be missed. Camera callbacks and tracks are stopped on camera failure or page exit; a page restored from browser back/forward cache reloads to restart the camera.

Test-mode readiness requires five consecutive frames with finite derived features. The capture policy retains a legacy-only readiness state for historical decryption regression compatibility; it cannot start a new test capture. The user-facing Vault does not expose historical-file decryption.

As a continuity hint, capture also rejects a frame if the normalized wrist or palm-center position moves more than 0.35 from the preceding frame, or the image-landmark bounding-box diagonal grows or shrinks by a factor greater than 2.5. A gap over 1000 ms between processed frames invalidates capture. These deliberately loose values are configurable experimental parameters, not measured optimal thresholds. MediaPipe handedness labels are not used as an identity check. A hand count of one, stable location, and stable apparent size **do not establish identity or liveness**. The detector can miss another hand, and a hand substituted at a similar position and size may pass. Camera spoofing is outside this policy's protection.

For manual browser checks on localhost, verify: enrollment requires two separate matching captures; each normal encrypt/decrypt starts a fresh capture; unsupported file formats receive the unsupported-format message before camera access; recovery works with camera permission denied; the backup and acknowledgement gate blocks an encrypted-file download until completed; and rebind retains the original file while issuing a different recovery key for the rebound file. Also verify one steady hand becomes ready, zero and two visible hands cannot start capture, a second hand entering near the beginning, middle, or last frame cancels capture, and permission denial or model failure produces a clear error. Record detector misses and false rejections rather than inferring security from synthetic tests alone.

Test-mode captures reject ratios within 0.04 of a threshold and applicable spread angles within 2 degrees of 12. Equality at the edge of a margin is accepted. Standard deviations above 0.12 ratio units or 6 degrees are rejected. These values are **experimental parameters**, selected as modest guard bands relative to the existing 0.40 ratio step and 12-degree spread threshold. They have not been tuned or shown optimal on a gesture dataset. Do not tune them on the final evaluation set. Record any future calibration protocol and keep evaluation data separate.

### Developer calibration diagnostic

For local diagnosis only, open `http://localhost:8000/?gestureDebug=1`, select **Test mode**, and inspect the browser developer console after each completed 25-frame capture. Accepted captures report their final signature; quantization rejections report their reason and no signature. Both report a table of **derived 25-frame medians and standard deviations**, nearest quantization boundaries, distances, margins, and whether each feature is applicable. Capture-state rejections before 25 frames have no summary to report. The diagnostic does not log camera images, individual landmarks, frame sequences, credentials, keys, or file contents. It is off by default, held only in the console, and absent from the CSV export. Treat derived measurements as sensitive and avoid sharing console output with participant identities.

To calibrate margins, keep the current 0.04 ratio and 2-degree spread settings as the baseline. Before changing them, preselect a small pose set (for example fist, open hand, and two mixed poses), camera setup, lighting, distance, and repetition order. Record 10 or more attempts per pose in each of two sessions, including slight natural repositioning; record rejected attempts and reasons as well as accepted-match outcomes. If another participant is available, report their results separately. Reserve one session as a holdout and use only the first for choosing candidate margins. Compare 0.02/0.04/0.06 ratio margins and 1/2/3-degree spread margins on the same completed-capture summaries while keeping the existing variability limits fixed. For each setting, report acceptance and rejection counts by pose, exact-match fraction against its reference, signature changes after small movements as mismatches, and borderline/unstable attempts rejected. Then apply the chosen setting to the untouched holdout session. Small samples cannot establish population reliability or security; retain rejected attempts in the denominator and state any missing data or detector failures.

### Study recording (Milestone 3)

Test mode includes a study recorder. Before a block, set anonymous participant/session IDs (`P01`, `S01`, etc.), intended pose, dataset split, trial relation, scene, observer-visible hand count, browser, camera, lighting, and the planned **physical-attempt** count. One click on **Start/replace reference** or **Run trial** is one physical attempt even if readiness or capture fails; its three configuration-specific CSV rows are not three attempts. Include planned references and planned retries in the count. Contingent retries increase the recorded count and may appear as overrun; do not erase or relabel them. Use **Protocol status** to mark a known missing or invalid observation; use **Exclude last attempt** immediately afterward for an unexpected protocol deviation. Excluded attempts remain in the record but are omitted from rate denominators. The on-screen log distinguishes reference and trial attempts, capture/quantization rejection, match/mismatch, and exclusions. **Clear display only** does not erase study records.

Select **New scheduled attempt** for a new reference or trial; its `retry_index` is 1. Select **Retry immediately previous compatible attempt** only when repeating the immediately preceding completed attempt under the same role, participant, session, pose, relation, scene, camera, lighting, and (for trials) reference candidate. The recorder derives index 2, 3, and so on and exports `retry_of_attempt_id`; the operator cannot type an index. Each reference attempt, including a failed one, is retained. A reference retry has the same `reference_group_id` as its predecessor but becomes the candidate `reference_id` for later trials; a new reference starts a new group. Starting a new reference while one exists requires confirmation and replaces only future comparisons. A rejected candidate leaves no active reference for that configuration. Prior groups and trial links remain in the export. Retry intent is an operator annotation, not something the camera can infer; verify it during collection.

For every completed 25-frame capture, the study-only shadow quantizer evaluates the same derived median/standard-deviation summary against three fixed configurations: `loose` (0.02 ratio/1 degree), `baseline` (0.04/2), and `strict` (0.06/3). Reference and trial are both recomputed for each. State-machine rejections do not get a signature under any configuration. A trial accepted under a configuration whose reference was rejected is recorded as `no_reference_for_config`, not a mismatch. The production quantizer and its margins remain unchanged.

Collect pilot/calibration attempts first. Inspect pilot exports, document a selection rule, then choose and **Freeze pilot choice** before any held-out attempt; this records an analysis decision and never activates new production margins. A fresh held-out tab may enter the reviewed pilot's anonymous study ID in **Reviewed pilot study ID** before freezing. That ID and selected configuration are recorded in JSON, but the app cannot verify the external pilot evidence: retain the original pilot CSV/JSON and written decision separately. Use a new held-out session ID and capture new held-out references; pilot references cannot be reused across splits or sessions. Report the frozen choice as the primary held-out result and label other configuration comparisons exploratory. Set planned counts before collecting each split; exports report physical attempts planned, initiated, uninitiated, and overrun. Export CSV and JSON after every block. Study state now has a versioned local browser recovery copy. On reload, review the restored ID and attempt count and confirm before resuming; an unfinished attempt becomes a non-match `interrupted` capture rejection with unknown timing. If the copy is corrupt, incompatible, unavailable, or changed by another tab, collection stops without replacing it. **End study and delete local recovery copy** requires confirmation; export the paired CSV/JSON first. Browser storage may still be cleared by the user or browser, so keep checkpoint exports. The recovery copy contains active reference signatures because comparisons require them; they are sensitive derived gesture data, stored unencrypted for this origin. Use a private local browser profile, avoid sharing it, and end the study after exporting. It never stores passphrases, encryption keys, plaintext, raw frames or landmarks. A new-session reference does not measure cross-session matching against the pilot reference.

The approved [held-out protocol](research-results/phase-4/heldout_protocol.md) specifies a separate session (`S02`) and a predetermined order for four poses: one reference, five genuine same-person/same-pose trials, and two same-person/different-pose trials per pose, for 32 scheduled physical attempts before contingent retries. It also predeclares retry and exclusion rules. The latest local checkpoint uses `S03`, one documented protocol deviation; preserve the original protocol and reconcile any final export against its scheduled slots rather than treating the arithmetic uninitiated count as slot completion. No threshold may be tuned or reselected using held-out results. Even a completed small convenience sample would not establish identity assurance or a population-level false-accept rate.

The routine CSV has one row per initiated attempt per configuration, linked by `attempt_id`; its fixed fields include anonymous IDs, split, role, pose, reference candidate ID, reference group ID, retry predecessor ID and index, relation, scene, observer-visible hands, capture and quantization outcomes, separate comparison status, rejection code, reference availability, match, timing, environment categories, and protocol status. The JSON contains schema/version values, a reviewed external pilot ID if supplied, the physical-attempt count unit, counts, exclusions, numerator/denominator/value triples, and latency summaries; zero-denominator values are `null`. Neither routine export contains signatures, derived feature summaries, raw landmarks or frames, credentials, keys, or plaintext. The comparison happens in memory; there is no calibration-summary export or opt-in signature export in this milestone. This protects privacy but means an outside researcher can recompute reported rates from the CSV, not re-run quantization from raw measurements. If consented participants are involved, use codes rather than names, restrict access to exports, and delete study copies by 4 December 2026 unless institutional policy requires another retention period. Developer console diagnostics remain separate and should not be shared with participant identities.

### Offline study analysis (Milestone 5)

With authorized access to a paired CSV and JSON export, run the analyzer from the repository root, substituting their actual paths:

```sh
python3 study_analysis.py "study.csv" "study_summary.json" --out "analysis-output/pilot-reproduction"
```

`study.csv` and `study_summary.json` above stand for the actual paired input files, not files supplied by this repository. Choose an output path that does **not** already exist; the script refuses an existing destination, creates a new directory, and never changes the source exports. It uses only the Python standard library. The exact original pilot CSV/JSON pair is retained privately outside the public repository and matches the input hashes in [the validated analysis](analysis-output/pilot-STUDY-1873C987/analysis.json). Reproducing that analysis requires authorized access to **those original files**; aggregate outputs alone cannot regenerate it. Do not substitute a later checkpoint. The analysis tests use `python3 -m unittest discover -s tests -p 'test_*.py'`.

The analyzer accepts study export schemas 1 and 2, checks CSV fields, three configuration rows per physical attempt, reference/retry links where available, protocol status, and the JSON's counts, rates, exclusions, and latency summaries. It stops with an error on disagreement. It writes `aggregate_metrics.csv`, `analysis.json`, and `report.md` at the new output directory's root, with six SVG figures in each populated `pilot/` or `heldout/` subdirectory. Pilot figures are labelled exploratory; an empty held-out split produces no held-out graphs. The aggregate and figures omit participant IDs, signatures, feature measurements, and credentials. Schema-1 pilot exports do not support reliable retry or reference-group reconstruction. Match rates use only trials with an available reference; rejected captures are counted as rejections, never mismatches. The analyzer does not calculate FAR/FRR or infer cross-session matching. `capture_ms` includes the wait for readiness, so it is not isolated frame-processing time.

The retained version-1 decryption module uses the original zero-margin quantization so historical test files with a borderline gesture remain representable in regression tests. New V3 files do not use gesture measurements or signatures as cryptographic key material. There is no forgotten-passphrase escrow; use the file-specific recovery key if normal V3 access is lost.

The automated v1 compatibility suite includes round trips and an independently encoded file, but the repository contains no genuine file archived from the pre-v2 application. To close this gap, use a non-sensitive `.gcry` file actually created by the older application and retain its creation version, expected filename, content hash, and test gesture/PIN in a restricted local test record. Verify decryption locally before adding it as a fixture. Commit it only if its plaintext and credentials were deliberately made public for testing; otherwise keep the fixture and credentials out of the repository and report the manual check separately. Do not call a newly generated or independently encoded file a historical fixture.

## File format and cryptography

### Current V3 Vault

The active V3 format uses a fresh random 32-byte DEK for each file, PBKDF2-HMAC-SHA-256 passphrase wrapping, a non-extractable profile AES-256-GCM key protecting that envelope, an independent random per-file recovery key and recovery envelope, and separate 12-byte nonces with 16-byte GCM tags. The writer uses 600,000 PBKDF2 iterations. Its parser validates version, algorithm IDs, lengths, filename, and iteration bounds before PBKDF2. The recovery and normal paths authenticate the complete header and file ciphertext before releasing plaintext. The visible filename is authenticated. The passphrase is not a substitute for the file-specific recovery key. A strong, unpredictable passphrase still matters: PBKDF2 raises the cost of guessing but does not make a weak passphrase strong.

### Historical V1/V2 formats — regression and Attack Lab only

The preserved implementations below support historical regression tests and synthetic Attack Lab fixtures. **The user-facing Vault neither encrypts to nor decrypts these formats.** Its V1/V2 rejection occurs before gesture capture, passphrase handling, key derivation, or fallback.

Version 1 stores `GCRY | version(1) | salt(16 bytes) | IV(12 bytes) | filename length(2 bytes, big-endian) | UTF-8 filename | ciphertext and 16-byte GCM tag`. PBKDF2-HMAC-SHA-256 uses 600,000 iterations and a random 16-byte per-file salt to derive a non-extractable AES-256-GCM key from `signature + "|" + PIN`. Encryption generates a random 12-byte IV. The complete header is authenticated as GCM additional data. Decryption validates the header and minimum tag length before PBKDF2, then releases plaintext only after GCM authentication succeeds. The filename is authenticated on successful decryption but remains visible in the file header.

Version 2 has this exact binary layout (offsets are zero-based, integers are unsigned big-endian):

| Bytes | Field |
| --- | --- |
| 0–3 | ASCII `GCRY` |
| 4 | Version `0x02` |
| 5 | KDF ID `0x01` (PBKDF2-HMAC-SHA-256) |
| 6–9 | PBKDF2 iteration count, uint32 |
| 10–25 | Random 16-byte salt |
| 26–37 | Random 12-byte key-wrap nonce |
| 38–49 | Random 12-byte file-encryption nonce |
| 50–51 | UTF-8 filename length `N`, uint16 |
| 52…51+N | Visible UTF-8 filename |
| 52+N…99+N | Wrapped 32-byte DEK plus 16-byte GCM tag (48 bytes) |
| 100+N…end | File ciphertext plus 16-byte GCM tag |

The writer uses 600,000 PBKDF2 iterations; the parser accepts 600,000–1,200,000. The filename must be 1–255 UTF-8 bytes and cannot contain path separators or control characters. The passphrase must be 1–1,024 UTF-8 bytes; new encryption also requires a nonblank passphrase of at least 12 Unicode characters. Length is a minimum usability guard, not an entropy measurement; use a long, unpredictable, unique passphrase. Both GCM operations use AES-256-GCM with 128-bit tags. A fresh random 32-byte DEK encrypts each file, and a passphrase-derived KEK wraps that DEK. The wrap AAD is UTF-8 `GestCrypt-v2-wrap`, a zero byte, then bytes 0…51+N inclusive. The file AAD is UTF-8 `GestCrypt-v2-data`, a zero byte, then bytes 0…99+N inclusive. All visible metadata is authenticated by the wrap operation; the full header is also authenticated with file ciphertext. The contexts are fixed and distinct. Decryption validates format, version, identifiers, lengths, and KDF bounds before PBKDF2; it releases no plaintext until both authentication checks pass. A v2 authentication failure never retries v1.

The preserved V2 module accepts plaintext files up to 32 MiB. Its encrypted size limit is 32 MiB plus the maximum 355-byte header and 16-byte file tag. V1 retains its original whole-file behavior without a new size cap. Browser memory can contain multiple copies of file and key material, and JavaScript strings cannot be reliably erased. V3 persists its non-extractable profile key and Vault gesture template in separate IndexedDB stores; it does not persist passphrases, recovery keys, or plaintext. GCM performs the tamper check.

## Security Attack Lab

Open **Security Attack Lab** and select **Run attack scenarios**. The lab creates small synthetic encrypted files in memory using the preserved encryption functions. It does not read the file picker, user-entered passphrase or PIN, camera data, or study records, and it does not download test plaintext. A camera started in Test mode may remain active after switching to the lab. Each row states the scenario, expected behavior, observed result, status, and relevant principle. The summary separates resisted attacks, the successful recovery control, failures, known limitations, and scenarios that could not run. PASS means the expected result was observed in that run, including successful recovery in the positive control; it is not a proof against all possible attacks.

The ten scenarios cover wrong passphrase; ciphertext-body changes in two synthetic formats; wrapped-key tag change; filename changes; IV and nonce changes; truncated files; unsupported format markers; format-marker rewriting; and synthetic file recovery with byte, filename, and hash comparison. Redirecting a passphrase-protected file toward the gesture-protected format can request gesture credentials because format selection occurs before authentication. The altered file returns no plaintext in the lab; this is a dispatch limitation, not a fallback after authentication failure. The lab does not test a genuine archived file from an earlier release, camera replay or liveness, offline guessing cost, or full-size cross-browser performance. It makes no biometric identity claim.

## Security limits and evaluation

For the historical v1 path, the signature format admits **at most 348 distinct strings** under the current quantization rules, before physical pose constraints and human choice patterns are considered. A 256-bit derived key does not mean the gesture has 256 bits of entropy. Anyone with a v1 `.gcry` file can test candidate gestures and PINs offline; salt and PBKDF2 increase the cost per guess but do not prevent guessing. An empty or short v1 PIN leaves weak protection. Historical V2 removes the gesture from key material, but an attacker with a v2 file can still test passphrase guesses offline. PBKDF2 slows each guess; it cannot rescue a predictable passphrase. These historical files are unsupported in the visible Vault. No strength claim is made without measurements.

Gestures are repeatable and observable. There is no challenge-response or liveness check, so a copied or imitated pose can be replayed. The optional PIN is simply additional key material; this project does not establish it as an independent authentication factor. Exact signature comparison in test mode is a repeatability experiment, not biometric identity authentication.

Test mode keeps active references and study records in memory and a local browser recovery copy. Routine CSV and JSON exports exclude signatures and credentials. A matching signature is a local equality result, not identity authentication; a rejected capture must never be counted as a mismatch. The one-participant pilot provides exploratory camera repeatability observations only. It does not establish general reliability, attack resistance, accessibility, or completed held-out performance.
