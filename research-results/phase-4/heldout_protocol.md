# GestCrypt Held-Out Gesture Study Collection Protocol

**Status:** Prepared for review; no held-out attempts have been collected. This protocol specifies one fresh reference, five genuine trials, and two same-person different-pose trials for each of four poses. It does not change the application or its production gesture margins.

## Experimental objective and primary decision

The objective is to estimate, in a separate session, how often a predefined hand pose produces an accepted signature and matches its newly captured reference. The eight different-pose trials test whether this one participant's deliberately different poses produce the same signature as a current reference. They are **same-person cross-pose probes**, not impostor or identity-verification trials. Record capture rejection, reference unavailability, and exact-signature mismatch separately. Do not use the held-out results to tune margins.

**Recommended frozen study configuration: `loose` (0.02 ratio units / 1°).** In the exploratory pilot, loose accepted **21/24 genuine trials (87.5%)** and **7/7 references**; baseline accepted **14/24 (58.3%)** and **5/7**; strict accepted **5/24 (20.8%)** and **1/7**. Loose produced **18/24 end-to-end matches with an available reference**, compared with **12/24** for baseline. Its **18/21 conditional matches** and **3/21 accepted mismatches** do not establish an optimal or safer threshold: the pilot had one participant, one session, and no different-pose trials. Strict's **3/3 conditional matches** rest on only three comparable accepted trials. Select loose as a **usability-focused primary evaluation setting**, while retaining baseline and strict as paired exploratory comparisons. This recommendation does **not** activate loose margins in production, and it is not a claim about impersonation resistance. The researcher must approve this choice and use **Freeze pilot choice** before the first held-out attempt; the protocol document alone does not set application state.

Use pilot study ID `STUDY-1873C987` as the reviewed source. Keep its [pilot analysis](../../analysis-output/pilot-STUDY-1873C987/analysis.json), [pilot results](../phase-3/results.md), and original CSV/JSON exports as the dated decision evidence. A different choice requires a written pre-collection amendment, not a change made after seeing held-out outcomes.

## Participants, session, and setting

Use the same anonymous participant code as the pilot, `P01`, **only if it is in fact the same participant**; otherwise assign a new code matching `P00`–`P999` and document the change before collection. Use a new session code, `S02`, and a fresh browser tab with a new generated `STUDY-...` ID. Do not reuse pilot references. The current UI does not enforce that the held-out session ID differs from the pilot, so the operator must check it. Keep the intended browser, camera, hand position, distance, lighting, and verbal instructions as consistent as practical; select the corresponding fixed environment categories before starting. Record deviations as protocol-invalid when they invalidate an attempt. Obtain consent under the local course or institutional process if any person participates; do not put names in exports or public notes.

Use `split=heldout`, `scene_condition=single`, and the observed hand-count category that the operator actually sees. This 32-attempt protocol contains no second-person, multi-hand, or replay trials. A single detected hand is not proof of the participant's identity or liveness.

This schedule has **4 references + 20 genuine trials + 8 different-pose trials = 32 scheduled physical attempts**. Each non-reference pose appears twice as a different-pose target. For slots 07, 08, 15, 16, 23, 24, 31, and 32, keep the **same participant ID** as the active reference, choose `different_pose`, and set `pose_id` to the pose actually performed. Do not select `impostor`. The reference candidate remains the most recent reference attempt for that block; the CSV retains its `reference_id` and schema-v2 `reference_group_id`.

**Implementation readiness:** the 32 scheduled attempts are executable with the current recorder and UI; a synthetic in-memory schedule check produced four reference, 20 genuine, and eight `different_pose` physical attempts without writing study data. No code change is required for the core schedule. Two conveniences are absent: the live result display is baseline-only, and the export has no detailed operator exclusion-reason field. This protocol uses paired snapshots and an anonymous operator log. If the study requires the frozen loose outcome or detailed exclusion reason **in the live interface or machine-readable export**, that would require a separate, tested tooling change before collection. The analyzer produces `different_pose` rows in its aggregate CSV, but its standard six figures do not include a dedicated different-pose chart.

## Collection and reference procedure

1. Before the first attempt, open GestCrypt on localhost in a fresh tab, select **Test mode**, allow camera access, and verify the preview and readiness feedback. Record the new study ID outside the application. The study exists only in this tab's memory; reloading loses it.
2. Set `P01` or the approved new anonymous participant code, `S02`, `heldout`, and the intended environment categories. Set **Planned physical attempts in selected split** to **32** and click **Set planned count** before any attempt. The plan cannot be revised after collection starts. Contingent retries add to recorded attempts and may appear as overrun.
3. Enter `STUDY-1873C987` in **Reviewed pilot study ID**, choose **Loose 0.02 / 1°**, and click **Freeze pilot choice**. Confirm the status message. Export the summary JSON before collection if desired and verify `frozen_config_id="loose"`, `pilot_source_study_id="STUDY-1873C987"`, and `planned.heldout=32`. The application validates the ID shape and freezes one supported configuration; it **does not verify the external pilot evidence or record a freeze timestamp**.
4. Work through the slots in order. Before each fresh reference, select its pose, `New scheduled attempt`, and `Valid`; click **Start/replace reference**. Accept the confirmation when moving to a new pose block. Do not press **Clear display only** to manage records; it clears the visible table, not the study history.
5. After each reference attempt, export a temporary paired CSV/JSON snapshot and inspect the newest row for `config_id=loose`. A loose reference is available only if its `quantization_outcome` is `accepted` and `protocol_status` is `valid`. This inspection is necessary because the **on-screen signature, match, and “current reference” display use the production baseline**, even though the recorder separately evaluates the frozen loose configuration. Keep the tab open and continue from the frozen-configuration result, not the baseline display. Snapshot exports are read-only copies; preserve the final paired export separately.
6. For each genuine slot, select the reference pose and `genuine`. For each different-pose slot, select the specified target pose and `different_pose`. Confirm the same participant and `S02` remain selected. Select `New scheduled attempt` unless applying the predeclared immediate retry rule below. Press **Run trial** once per physical attempt, including an attempt that fails readiness or capture. Record the protocol slot and generated attempt ID in an anonymous operator log so shifted IDs can be reconciled after retries.
7. Export paired CSV and JSON snapshots after each pose block and immediately at the end. Use distinct filenames or a study-ID-specific folder; do not overwrite the pilot or an earlier snapshot. The app cannot restore its active reference or study history after a reload. If the tab is lost, stop and report the incomplete session instead of silently merging a new study ID into this one.

### Retries and exclusions

Keep each scheduled slot in the record even when rejected or mismatched. A valid capture or quantization rejection is an **outcome**, not a protocol exclusion. Do not retry solely because an accepted trial mismatched the reference.

For a reference rejected under the **frozen loose** configuration, allow at most **two immediate reference retries** before the first scheduled trial in that block. After each retry, re-export and inspect the loose reference outcome. Select **Retry immediately previous compatible attempt** with the same participant, session, reference pose, scene, camera, and lighting. A retry has `retry_index` 2 or 3 and `retry_of_attempt_id` pointing to its predecessor; it retains the reference group but becomes the new candidate reference. If all three reference attempts fail, still initiate the seven scheduled trial slots, reporting `no_reference_for_config` where applicable. Do not call those trials mismatches.

For a trial with a camera or capture-state rejection, allow at most **one immediate retry** under the same metadata and reference candidate. Do not retry an accepted mismatch or a frozen-configuration quantization rejection. An immediate retry must occur before the next scheduled slot; the UI resets **Attempt kind** to **New scheduled attempt** after each capture, so select **Retry** explicitly. If an interruption prevents immediate retry, record the rejection and continue; do not label a later attempt as its retry. All retries are additional physical attempts and increase `recorded`; the 32 scheduled slots remain unchanged.

Set **Protocol status** to `missing` or `protocol_invalid` when known before an attempt. For an unexpected deviation discovered just after capture, use **Exclude last attempt** immediately, before starting another attempt. This changes the last record to `protocol_invalid` but retains it and clears an excluded reference from active comparisons. The export records only the coarse status (`valid`, `missing`, or `protocol_invalid`); it has **no separate field for a detailed operator exclusion reason**. Keep an anonymous local slot-to-attempt log with a short fixed reason such as `wrong_pose`, `operator_error`, `camera_setup_deviation`, or `interruption`; do not add names, signatures, or feature measurements. If a reference is excluded, an immediate reference retry is allowed under the same cap. Do not remove excluded attempts from recorded counts, and omit them from valid performance denominators.

## Expected export schema and integrity checks

The current recorder emits **schema version 2**. The routine CSV includes `study_id`, `app_version`, unique `attempt_id` within that study, `participant_id`, `session_id`, `split`, `role`, `pose_id`, `relation`, `reference_id`, `reference_group_id`, `retry_of_attempt_id`, `retry_index`, `config_id`, `capture_outcome`, `quantization_outcome`, `comparison_status`, `rejection_code`, `reference_available`, `signature_produced`, `match`, `attempt_ms`, `capture_ms`, `protocol_status`, and scene/environment categories. Each initiated physical attempt has exactly one `loose`, one `baseline`, and one `strict` CSV row. With **no retries**, 32 attempts produce **96 CSV data rows**. `attempt_id` is unique only within a `study_id`; use the pair when reconciling files. The CSV does not include the frozen choice or pilot source ID.

The paired JSON includes `schema_version=2`, `planned_unit="physical_attempts"`, `planned.heldout=32`, `recorded`, `uninitiated`, `overrun`, `exclusions`, `exclusions_by_status`, `frozen_config_id="loose"`, and `pilot_source_study_id="STUDY-1873C987"`, plus per-split, per-configuration, per-relation rates and latency summaries. It has `recorded.pilot=0` in a fresh held-out tab. Without retries, interruption, or exclusions, expect `recorded.heldout=32`, `uninitiated.heldout=0`, and `overrun.heldout=0`. With `R` additional retries after all scheduled slots, expect `recorded.heldout=32+R` and `overrun.heldout=R`. If collection stops early, the counter `uninitiated=max(0, 32-recorded)` is only an arithmetic count: retries can hide uncompleted scheduled slots, so the operator log must also identify completed slots.

After collection, run the offline analyzer on the **paired** final CSV and JSON using a new output directory. It validates the schema, three-row pairing, unique study/attempt/configuration tuples, split and protocol codes, reference and retry links, supported frozen configuration, and JSON counts, rates, and latency summaries. It rejects inconsistent pairs rather than repairing them. Check the output source hashes against the archived exports. Keep pilot and held-out data in separate study IDs and report sections; do not combine them into a single performance figure. Routine exports do not contain raw signatures, feature summaries, frames, credentials, or keys.

Before accepting the dataset, verify all 32 scheduled slots against the operator log; exactly four reference blocks; 20 scheduled genuine and eight scheduled `different_pose` trials; no `impostor` rows; the approved participant and `S02`; the expected reference candidate and group for each block; retry predecessor and index; all three configurations for each attempt; excluded and missing counts; and the two freeze fields in JSON. A `no_reference_for_config` status can overlap a capture or quantization rejection. It must never be converted to a mismatch.

## Metrics and interpretation

Report the **frozen loose configuration as primary**. For reference attempts, report accepted/valid references with numerator and denominator, including retries separately from scheduled references. For genuine trials, report signature acceptance and rejection over valid genuine attempts; end-to-end exact matches over valid genuine attempts **with a reference**; and conditional exact matches over accepted genuine attempts **with a reference**. Report accepted mismatches, capture-state and quantization rejection codes, reference-unavailable counts, exclusions, scheduled and retry counts, and attempt/capture latency with sample count, median, minimum, and maximum. Distinguish scheduled-slot outcomes from retry outcomes if retries occur.

For `different_pose`, report the number of valid same-person cross-pose attempts, accepted signatures, rejected attempts, accepted exact matches and mismatches **with an available reference**, and reference-unavailable attempts. Give exact numerators and denominators; call any exact match a **cross-pose signature collision in this protocol**, not an impostor acceptance or FAR. The current analyzer's aggregate CSV includes the `different_pose` relation and its rates, while its six standard figures emphasize genuine trials and reference acceptance; make a clearly labelled table for the different-pose results rather than treating the genuine figures as covering them. Baseline and strict remain paired **secondary exploratory** comparisons; do not reselect the primary configuration after viewing held-out results. A zero denominator is `null`/not applicable, not 0%.

## Limits and threats to validity

One participant and one held-out session would still be a small convenience study. Fresh session references measure within-session matching after recapture, **not** cross-session matching to the pilot reference. Different-pose trials with the same person do not test another person reproducing a gesture. The camera policy cannot identify the intended person or prove liveness. No identity, biometric authentication, replay prevention, impersonation resistance, or population-level FAR/FRR claim follows from this protocol. V2 passphrase-based file protection is cryptographically separate from test-mode gesture matching; legacy v1 has a different gesture-derived path.

The study records categorical browser, camera, and lighting codes rather than precise hardware or illumination. Readiness and `capture_ms` include waiting before 25-frame completion; `attempt_ms` can additionally include camera startup. The operator can misclassify visible hands, poses, retry intent, or exclusions. Routine exports omit derived feature measurements, so a new threshold cannot be recomputed offline. The analyzer checks the exported frozen ID but cannot prove *when* the UI choice was made or that the external pilot was independently reviewed. The primary protocol therefore relies on the pre-collection decision record, the paired exports, and the operator's slot log.
